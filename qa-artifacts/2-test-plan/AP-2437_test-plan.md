## 1. Test Objectives

- Verify that all acceptance criteria in **REQ-001 through REQ-005** are met: the
  acceptance-or-waiver form is inserted into the Chubb insurance contract PDF
  automatically, on the first page, in the correct one of four language-and-rate
  variants, carrying the four required disclosures, inside a PDF that opens, prints and
  reads correctly.
- Prove that the historical failure this story exists to fix — the
  `Zend_Pdf_Exception: PDF file syntax error. Offset - 0x2F862C. Wrong W dictionary
  entry.` raised when merging Chubb's PDF 1.7 file — no longer occurs, and that the
  Chubb-supplied pages and their client data survive the merge unchanged.
- Establish, before execution rather than during it, whether the environment can
  actually run the feature: whether the `qpdf` binary the fix depends on is installed on
  the staging host, and whether a tester can reach a Chubb creditor-insurance contract
  and steer its rate and language to exercise each of the four decision branches.
- Confirm that the change did not break contract printing elsewhere. The merge engine was
  replaced for this code path only, so every other feature still generating PDFs through
  `Zend_Pdf` is now on a divergent path and must be re-checked.
- Surface, as written questions on the ticket rather than as guesses in a test result,
  the one rule the story never states: which of the four attached PDFs each decision
  branch selects.

## 3. Test Strategy

### 3.1 Test Levels

*A test level says how much of the system is exercised at once. This effort works
entirely at the outer levels, because the QA pipeline drives the deployed application
through a browser and has no access to the source code.*

| Level | Description | Responsible |
|---|---|---|
| System Testing | End-to-end validation through the dealer portal in a real browser: create or open a Chubb creditor-insurance contract, download the PDF, inspect the produced file. This is the primary level for every requirement in scope. | QA Agent |
| Integration Testing *(observational)* | The merge depends on two things outside the portal — Chubb's live `/contract` API and the `qpdf` binary on the host. We cannot instrument either, but we verify their effects: that a live call produced a real contract, and that no server error was raised. | QA Agent |
| Regression Testing | Re-running checks that passed before this change, to confirm the change did not break them. Two areas: contract printing for other product lines still using the old PDF library, and the AP-2436 compliance-document flow, which touches the same Chubb configuration. | QA Agent |
| Unit Testing | N/A for this pipeline — no codebase access. Assumed covered by the three merged pull requests. | Development team |
| User Acceptance Testing | N/A for this cycle. Not requested, and the story is still at QC. | Product owner (future) |

### 3.2 Test Types

| Type | Approach |
|---|---|
| Functional | Walk each acceptance criterion end to end and confirm the observable outcome: the form is present, it is on page 1, it is the right variant, it carries the four disclosures, the PDF opens. |
| Negative | Drive the feature into its failure paths on purpose — a contract whose Chubb call fails, a dealership whose Chubb configuration is absent, and, if a host without `qpdf` can be reached, a download on that host. The question each time is whether the dealer sees a clear failure or a silently incomplete contract, because a contract missing its legal disclosure that *looks* complete is the worst outcome this story can produce. |
| Edge-case | The substring rule is the interesting boundary here. "Rate contains 50" matches "150", "50.5" and "PM50" as readily as "50", and no one has said whether that is intended. Also: a contract carrying more than one insurance product, and an unset or unrecognised language value falling through to the default branch. |
| Regression | Re-run a warranty or invoice PDF download to confirm the untouched `Zend_Pdf` path still works, and re-run one AP-2436 compliance send to confirm the shared Chubb configuration was not disturbed. |
| UI | Visual confirmation by screenshot at each verification step: the download control, the produced file, and the first page of the opened PDF. |
| API *(indirect)* | The Chubb `/contract` endpoint is exercised implicitly by every download. We do not call it directly; we observe whether the portal handled its response. |
| Performance *(observational)* | Record the elapsed time from clicking download to receiving the file. Every download now performs a live external API call, an external `qpdf` process and a PDF merge. There is no stated target, so results are recorded as observations, not as pass or fail. This is Q-not-yet-asked: if the product owner supplies a target, this becomes a real assertion. |

### 3.3 Test Execution Method

All manual test cases will be executed by the **stlc-manual-executor** skill through the
project's bound `browser` provider — **Playwright**, per
[qa-artifacts/qa-config/tools.md](../qa-config/tools.md) §1. The agent navigates the
dealer portal at 1280 × 800, captures screenshots as evidence into
`qa-artifacts/4-execution-results/screenshots/{Sprint}/AP-2437/`, and logs a Pass or Fail
against each step.

**One execution constraint is specific to this story and must be stated up front.** The
deliverable is a **downloaded PDF file**, not a page in the browser. A browser-driven
agent can click the download control and confirm a file arrived, but confirming what is
*inside* that file — page order, page count, the text on page 1, whether the client data
survived — requires opening the PDF. Where the browser's built-in PDF viewer renders the
file in a tab, the agent can read it from the accessibility snapshot. Where the file
downloads to disk instead, the agent must inspect it outside the browser. Test cases
must state which of the two applies, and any case that cannot be verified by either route
is to be marked BLOCKED at design time rather than passed on the strength of "a file
downloaded".

## 6. Suspension and Resumption Criteria

### Suspension

Testing is suspended if:

- The staging portal is inaccessible for more than 30 minutes.
- Contract download fails with a server error on the very first attempt — this most likely means `qpdf` is not installed on the host, which makes every remaining case unrunnable. Raise it immediately as a High-severity defect rather than working through a queue of cases that will all fail the same way.
- More than 30 % of the test cases are blocked by one defect.
- The Chubb `/contract` endpoint is unavailable, since no contract can be produced without it. Distinguish this from a portal defect before reporting.
- A produced contract is found to contain another client's data. Stop everything and escalate — that is a data-leak incident, not a test failure.

### Resumption

Testing resumes when the blocking condition is cleared and a smoke check passes: log in
to the dealer portal, open one Chubb creditor-insurance contract, download it, and
confirm a valid PDF arrives. Any test case that had already failed under the blocking
condition is re-run from the start rather than resumed mid-case.
