Overview

Typing a ticket key such as AP-1234 runs the whole test cycle for that one ticket. The agent captures the ticket as a requirement, analyses it, plans and designs test cases, executes them in a real browser, files bugs, writes the test report and posts the result back on the ticket.

One new skill, stlc-ticket-pipeline, drives the existing STLC skills in order. It stops at four review gates, keeps every file scoped to the ticket, and resumes where it stopped when you type the key again.

This guide is for a QA engineer who already runs this STLC skill framework and wants to add the same one-key pipeline to another project. It covers what to build, which files to change, and the few project-specific settings to fill in.

Architecture

The orchestrator holds no QA logic of its own. It runs each stage skill in a fixed order, checks that the stage's file exists, and stops at a gate where a person should decide.

Gates A and B are about quality and can pass on their own with --auto. Gates C and D write to the shared tracker, so they always wait for you.

GateWhenWhat you decide
AAfter analysisContinue, post the open questions on the ticket and stop, or stop
BAfter peer reviewExecute current cases, promote the proposed cases first, or stop to edit
CBefore filing bugsPer failure: file new, comment on an existing duplicate, or not a bug
DBefore the status changeMove the ticket to the mapped qa_done status, only when the verdict is PASS

Three design rules keep long runs reliable:

  • Files are the contract between stages. Each stage reads the previous stage's files and writes its own, using the per-ticket paths in ticket-scope.md. No stage depends on chat context, so any stage can be re-run alone.
  • A stage is done only when its file is on disk. The run-state file records each stage as pending, running, done, skipped or failed, and the done-check is re-verified on every resume.
  • Execution runs in a subagent. Browser snapshots are large; isolating s4 keeps the main context small. The subagent may not ask the user anything; it returns its question, and the orchestrator asks it.

Intake also checks the ticket's status. Anything other than ready_for_qa asks first, and in --auto mode stops after design. A ticket of type bug switches to a re-test flow: it skips analysis, planning and review, and a failure becomes a comment on the same ticket, not a new bug.

Build steps

The build is three new files for the orchestrator, one new shared contract, and small edits to eleven existing files. Copy the new files from the Avantage repo; make the edits by hand, in this order.

  1. Create the per-ticket path contract .claude/skills/ticket-scope.md.
    • Defines the tokens {KEY} (ticket key as the tracker returns it), {SPEC} (key without punctuation, the test-case ID prefix), {SLUG}, {RUN} (sprint, else fix version, else asked once) and {DATE}.
    • Lists the path of every artifact per ticket, e.g. qa-artifacts/2-test-plan/{KEY}_test-plan.md, and states that these override each skill's default path.
    • Rule that matters most: never overwrite an existing requirement capture; append a dated section.
  2. Create the orchestrator .claude/skills/stlc-ticket-pipeline/.
    • SKILL.md (≤ 150 lines): inputs and flags, Step 0 provider resolution, run-state load/resume, Intake, the stage loop, close-out, Rules, Next Move.
    • routing.md: the Intake procedure, the stage table (skill, inputs, done-check, gate), the four gate definitions, the bug re-test flow and failure handling.
    • template.md: the run-state file, the requirement-capture template, the run summary and the ticket comment.
  3. Point every stage skill at the contract. In each of the eight stlc-* stage skills, add one Ticket scope blockquote under the purpose line. Three skills get one extra sentence:
    • stlc-requirements-analyst: read only the capture file passed in, not all of requirements/.
    • stlc-bug-reporter: apply the Gate C decisions (file new, comment on existing, not a bug).
    • stlc-ticket-updater: the target ticket and comment are passed in; still ask before any status change.
  4. Add the search capability. In .claude/skills/mcp-tools.md §3, add tracker.search_tickets; in §7, add the stlc-ticket-pipeline row. Add a tracker.search_tickets row to each tracker adapter's Capability map (see the table below).
  5. Route the ticket key. In agent-coordination/SKILL.md, add Step 0 — Ticket Key Rule with the key pattern, an s0 menu option in both menus, and the exception in Rules. In agent-coordination/routing.md, map stlc-ticket-pipeline to the "After test report" next-step group. In QA_AGENTS.md, add the bare-ticket-key exception to the auto-invocation rule.
  6. Register. Add the skill to ARCHITECTURE.md (STLC table, shared documents, folder trees), add a load-set row to qa-artifacts/qa-config/knowledge.md §2, and add ../ticket-scope.md to the allowed relative-path exceptions in scaffold-skill/checklist.md.
  7. Audit. Run scaffold-skill in REVIEW mode on stlc-ticket-pipeline and fix every failing item.

Porting to another project

Copy all of .claude/skills/ unchanged; only the project-owned files below change. No skill file names a provider, a URL or a path that belongs to one project, so the skills stay as they are.

FileChange for the new project
qa-artifacts/qa-config/tools.mdSet the tracker row to the new provider (jira, openproject, …) and browser to playwright, both active
repo-root .envTracker URL, project key, login and API token. Never commit it
qa-artifacts/qa-config/knowledge.mdBind env, test-data, navigation and domain to the new project's files; keep the stlc-ticket-pipeline load-set row
qa-artifacts/base-test/The new app's URLs, accounts, test data and navigation map
Tracker adapter Vocabulary mapMap canonical statuses to the new workflow, at least ready_for_qa (Intake check) and qa_done (Gate D). An unmapped status makes Gate D skip the transition instead of guessing
.mcp.jsonRegister the Playwright MCP server
Ticket key pattern (agent-coordination Step 0)Change only if keys are not ABC-123. An OpenProject project uses bare numbers, so use ^#?[0-9]+$
qa-artifacts/.session-state.mdStart empty; stlc-init-workspace seeds it

If the new tracker has no adapter yet, write .claude/skills/providers/<name>.md following the adapter contract in mcp-tools.md §8. Include a tracker.search_tickets row, or mark it Unsupported; Gate C then treats every failure as a new bug.

Run stlc-init-workspace once to create the qa-artifacts/ folders, then try one ticket with --until s3b to check intake and design before you let the pipeline drive a browser.

Using it

Type the ticket key on its own. Add a flag to change how far or how freely the run goes.

You typeWhat happens
AP-1234Full run, stopping at all four gates
AP-1234 --autoGates A and B take their default; C and D still ask
AP-1234 --until s3bCapture, analyse, plan, design and review only; no browser
AP-1234 --from s4Re-execute and re-report, keeping earlier artifacts. Use it to re-test after a fix
AP-1234 --statusPrint the run-state table and stop
AP-1234 again after a stopOffers to resume from the next pending stage, restart, or stop

The run state lives in qa-artifacts/.pipeline/AP-1234.md. On every start the pipeline re-checks that each done stage's file is still on disk, so a deleted artifact is regenerated, not trusted.

One run leaves these files behind:

  • requirements/AP-1234-<slug>.md — the ticket transcribed word for word
  • qa-artifacts/1-requirements-analysis/AP-1234_requirements-analysis.md
  • qa-artifacts/2-test-plan/AP-1234_test-plan.md
  • qa-artifacts/3-test-cases/AP1234_TestCases_001-005.md (and further batches) plus AP1234_ReviewFindings_<date>.md
  • qa-artifacts/4-execution-results/<run>/execution-log_AP-1234_<date>.md and screenshots
  • qa-artifacts/5-testing-report/AP-1234_bug-report.md and AP-1234_test-report.md
  • Bug tickets in the tracker and a summary comment on AP-1234

Troubleshooting and known limitations

SymptomCauseFix
Run stops at Intake: "not found"Wrong key, or the tracker CLI points at another projectRun the adapter preflight (jira.sh me) and check the project key in .env
Run stops after s3b without askingbrowser is not active, or --auto saw a status other than ready_for_qaBind the browser in tools.md, or move the ticket to the QA status
s4 marked failed: environment downThe c2 health check could not reach the login pageFix the environment, then <KEY> --from s4
Many BLOCKED, few FAILLogin, timeouts or 5xx before the step under testExpected: these are environment problems, not bugs. Check env and test-data
Gate D says the status has no mappingqa_done is not in the adapter's Vocabulary mapAdd the mapping once the team agrees which status means "QA passed"
A stage says done but the run marks it failedIts artifact is missing from the ticket-scope pathThe stage skill wrote to its default path; check its Ticket scope line

Known limitations:

  • Attachments are listed by name in the capture, not read. Open any mock-up or spec that matters and add a scope note to the capture by hand.
  • One ticket per run. A sprint-wide run would loop this pipeline over tracker-fetch-sprint-tickets and is not built yet.
  • The duplicate search is keyword-based and can miss a duplicate worded differently; Gate C keeps a person in that decision.
  • Subagent execution for s4 needs a runtime that offers subagents (Claude Code does). Elsewhere s4 runs inline and uses more context.
